# Запуск для жюри

Нужны Python 3.10+ и IDE с LLM-ассистентом (например, Codex или Cursor).
Python-инструменты не требуют библиотек и ключей. Сама LLM предоставляется
IDE и может требовать подписку, сеть и доступы. Они не включены в репозиторий.

1. Откройте корень репозитория в IDE (папку с `AGENTS.md` и `scripts/`). Дайте ассистенту прочитать `AGENTS.md`.

   Единый вход: `python scripts/start.py examples/campus-strategy/project.json`.
   Команда только читает файлы: показывает ограничения, рекомендацию, следующий
   вопрос и проблемы оснований. Для машинного вывода добавьте `--json`.
2. Отправьте запрос:

> Открой examples/campus-strategy/project.json. Выполни `python scripts/start.py examples/campus-strategy/project.json --json`, проверь источники.
> Объясни, какое решение требуется, почему рекомендуется O1 и что могло бы изменить
> выбор. Не считай синтетические обращения реальными. Выбор за меня не фиксируй.

3. Для нового анализа создайте отдельную папку:

```text
python scripts/project_tool.py new projects/my-case --title "Мой продукт" --objective "Какое решение нужно принять"
```

Передайте документы, таблицы и открытые ссылки. Ассистент уточнит рамку,
предложит план и выполнит исследование по workflow. Для значимого выбора он
покажет альтернативы; сохраняемое состояние находится в `project.json`.

4. Остановите чат. В новом чате укажите тот же файл и попросите продолжить.
5. Перед использованием вывода:

```text
python scripts/project_tool.py audit examples/campus-strategy/project.json --ready
python scripts/ledger.py report examples/campus-strategy/project.json
python scripts/project_tool.py report examples/campus-strategy/project.json --out examples/campus-strategy/outputs/decision-brief.md
```

`--ready` проверяет наличие структуры и координат evidence, не качество
рассуждений. Истинность, значимость вариантов и решения проверяются человеком.
Чтение сайтов не автономно: используются браузер/поиск текущей IDE.

## Поведение при сбоях

Если сайт недоступен, агент сохраняет блокер, использует уже прочитанные
материалы и отмечает, какой вывод нельзя подтвердить. Он не имитирует доступ.
Если файл изменился, `resume` перечисляет зависимые evidence и варианты;
экспорт блокируется до пересмотра. Прежний экспорт может устареть — запускайте
аудит перед передачей отчёта. Не включайте ключи, настоящие интервью и данные
студентов в папку проекта.

## Проверка без модели

```text
python -m unittest discover -s tests -v
python scripts/verify_demo.py
```

Вторая команда использует временную копию: меняет источник, проверяет отказ
экспорта, восстанавливает источник и проверяет недоступный файл. Результат —
`docs/verification.json`. Это не сравнительная оценка качества LLM.

Новые действия записываются через `ledger.py log`; `runs.jsonl` и команда
`project_tool.py costs` оставлены для чтения старых записей. Не складывайте
два журнала без проверки повторов.


## Структура, содержательная проверка и результат — отдельно

`audit --ready` проверяет структуру и необходимые именно этой задаче виды
источников из research_requirements. Таблица не нужна, если она не нужна решению.
`audit --ready --quality` дополнительно проверяет контракт support,
validation_design и strategy_review. Методика: workflows/decision-review.md.
Пример полного контракта: examples/review-contract-case/project.json.

Обычный `report` экспортирует видимый черновик. Для записки, прошедшей оба
уровня проверки, используйте `report <project.json> --out <path> --final`.
Даже такая записка не является независимой проверкой истинности или спроса.
planned не равно completed; для результатов нужны фактические артефакты.

Время журналирования: `--retrospective` для работы, записанной задним числом;
`--duration-s 1.2 --duration-basis measured` только при реальном измерении с
пояснением в --note. elapsed_s между begin/finish не является длительностью
исследования. Для измеренной нулевой длительности допустимо 0, оно сохраняется.
