# Сопровождение после решения

При запуске и продолжении агент строит сводку из имеющихся обязательств,
показателей, источников и checkpoints. Никакого фонового сервиса, автоматической
рассылки, переноса сроков или выбора за владельца.

## Запуск

```sh
python scripts/start.py projects/my-case/project.json --json
python scripts/follow_up.py inspect projects/my-case/project.json
python scripts/follow_up.py report projects/my-case/project.json --out projects/my-case/follow-up-2026-11-19.md
```

В сводке есть commitments/overdue_commitments, metric_results/new_results,
source_alerts, evidence_alerts и human_questions. Каждый пункт связан с ID и
JSON-путём исходного объекта; у вопросов есть причина и конкретное действие.
Сводка также включается в общую записку. Старые кейсы не требуют миграции.

## Сроки и согласование

К прежним owner/metric/due/review_trigger добавляются необязательные
commitment_id, status, agreement_reference и timezone. Для текущей просрочки
нужны записанное согласование, активный статус agreed/in_progress/blocked
и прошедший срок. completed/cancelled исключены; proposed и записи без статуса
или согласования требуют уточнения, а не объявления просрочки. Ссылка на
согласование фиксирует действительный ответ человека; скрипт не доказывает её смысл.

Часовой пояс задаётся в timezone проекта, при необходимости у обязательства.
Дата YYYY-MM-DD означает весь местный день: просрочка начинается в следующую
полночь. У точного timestamp просрочка начинается после указанного момента.
Сравнение проводится в UTC. Без зоны дата/локальное время не угадываются;
timestamp с явным смещением можно оценить независимо от зоны проекта.

Поддержаны UTC, явные смещения и IANA-зоны из доступной базы Python/ОС. В Windows
база может отсутствовать: для Europe/Moscow предусмотрен явно ограниченный
UTC+03 fallback с 27 октября 2014; исторические правила он не имитирует. Для
других отсутствующих зон нужно указать смещение или предоставить tzdata.
Неоднозначное/несуществующее время DST требует явного смещения. Новых обязательных
зависимостей нет. Истечение source.valid_until использует тот же календарный день
проекта, включая аудит и проверку оснований; для старых проектов без зоны — UTC.

## Результаты и отметки рассмотрения

metric_results связывает результат с конкретным commitment_id и точным metric,
value/unit, offset-aware observed_at, evidence_ids и data_origin real/synthetic.
Реальное наблюдение не может опираться только на описание источника, модельную
гипотезу или синтетику. Будущие/непроверенные результаты видны с причиной и
блокируют acknowledge и итоговый экспорт. Инструмент не делает численного
вывода о достижении цели из произвольного текстового review_trigger.

После фактического чтения агент явно сохраняет отметку:

```sh
python scripts/follow_up.py acknowledge projects/my-case/project.json --result-ids R1,R2 --reviewer "agent self-review" --note "проверены источники, требуется решение владельца"
```

follow_up_reviews хранит result_id, version_hash, реальное reviewed_at, автора
и заметку. Версия включает результат, связанные evidence/источники и критерий
review_trigger, но не перенос срока или служебные отметки. Изменение основания
или критерия делает версию новой для рассмотрения. Непрочитанное старое измерение
тоже новое для текущей работы — время само по себе не означает рассмотрение.
Отметка из будущего относительно часов среза не применяется к более раннему срезу.

Повторная отметка той же версии — no-op без изменения project.json и ledger.
Открытие всегда без записи. Сохранение использует атомарную запись состояния,
журнал и проверку конкурентного изменения из существующих инструментов. При
частичном сбое журнала команда сообщает, что отметки уже сохранены: прочитайте
состояние перед повтором. Это не распределённая транзакция нескольких писателей.

Рассмотрение НЕ означает одобрение. Вопрос остаётся в human_questions до
реального ответа: human_decision содержит reference и точный version_hash.
Смена версии снова требует решения. Отметки чтения исключены из хеша стратегии,
новые результаты и решения — нет. Сами статусы, сроки и выбранный вариант
инструмент не меняет. Полноту и смысл согласования проверяют LLM и человек.

## Актуальность оснований

Используются текущие fingerprints и последняя контрольная точка, явно заданный
valid_until и статусы stale/withdrawn/contradicted с существующим транзитивным
обходом зависимостей. Никакого произвольного «источник старше недели» нет.
Если источник удалён из реестра, показывается ссылка на checkpoint; исторический
эффект удаления на выбранный вариант не угадывается.

## Демонстрация и ограничения

```sh
python scripts/follow_up.py inspect examples/decision-follow-up-case/project.json --as-of 2026-11-19T10:00:00+03:00
python scripts/verify_follow_up_demo.py
```

Все выборы, согласования и значения в примере ВЫМЫШЛЕНЫ. R1 рассмотрен, R2 ещё
новый; C1 просрочен, C2 в срок, C3/C4 закрыты, C5 не согласован. Проверка работает
во временной копии: два открытия без записи, явное рассмотрение R2 без одобрения,
повторный no-op, изменение файла основания и новое требование пересмотра.
Это механическая проверка, не настоящий пилот или измерение эффективности.

--as-of — воспроизводимые часы оценки имеющегося состояния, не машина времени
и не доказательство того, какие файлы/решения существовали тогда. Прочие проверки
агента продолжают проверять текущие файлы. Автоматического получения метрик из
сервисов, мониторинга при закрытом проекте и независимой верификации смысла нет.
