# Осуществимость отдельно от согласования

Проблема из парного прогона: допуск локального прототипа был принят за достаточно
прояснённую осуществимость, после чего агент перешёл к бумажному протоколу.
Теперь start/resume, аудит и записка показывают отдельный раздел feasibility.

## Что проверяется

- Разрешение на минимальный объём.
- Полнота работ, требуемые компетенции и человеко-часы с основаниями оценок.
- Доступность и подтверждённая ёмкость каждого обезличенного ресурса в общем окне.
- Предлагаемое распределение нагрузки без превышения ёмкости одного исполнителя.
- Внешние зависимости и отдельно обоснованное календарное соответствие.

Исходы: **feasible** — указанный план согласуется с записанными условиями;
оценочные работы и календарный план остаются допущениями, не гарантией срока.
**infeasible** — в этом объёме/распределении есть подтверждённый запрет, недоступный
исполнитель, критический блокер или превышение подтверждённой ёмкости по
записанной оценке. Это не доказательство невозможности любого другого плана.
**unknown** — данных недостаточно или записанное окно уже закончилось.

Согласие на прототип не заполняет ресурсы. Unknown не переводит рекомендацию
на бумагу автоматически. Если доступность есть, а часов нет, результат unknown.
Если сумма часов укладывается, а календарная последовательность неизвестна,
результат тоже unknown. Неизвестные значения — null, не ноль.

## Использование

```text
python scripts/feasibility.py prepare projects/<id>/project.json --review-id F1 --option-ids O1,O2 --out projects/<id>/feasibility-F1.json
# Заполнить шаблон по фактическим материалам; не придумывать подтверждений.
python scripts/feasibility.py record projects/<id>/project.json --review projects/<id>/feasibility-F1.json
python scripts/feasibility.py report projects/<id>/project.json
python scripts/start.py projects/<id>/project.json --json
```

Состояние хранится только в append-only по процедуре `feasibility_reviews`;
инспекция вычисляет итог из последней записи, не сохраняет параллельный вывод.
Используются существующие baseline, source fingerprints, support_blockers,
record_review, журнал и защита выходных файлов. Новые источники/содержательные
изменения делают проверку stale. Новая запись требует обновить strategy_review.
Ресурсные входы последней записи также входят в baseline других разборов:
изменённый объём, ёмкость или календарный план требуют повторного стресс-разбора
и сравнения исследований. Собственный baseline исключает эту запись, поэтому
нет цикла взаимной инвалидации. Старые кейсы без feasibility не меняют хеши.

Контекст live_project требует фактических оснований owner_input или
project_observation. authored_example допускает проверку содержания вымышленного
условия и всегда помечается. Старые кейсы без новой коллекции совместимы;
not_recorded означает «не проверено», а не «ресурсов хватает». Неизвестное показано
как advisory с целевым уточнением; явный дефицит рекомендованного/выбранного пути
блокирует ready-экспорт. Старые основания не удаляются ради успешной проверки.

## Ограничения

Скрипт проверяет структуру, происхождение и арифметику записанного плана. Он не
проверяет личность, смысл каждого подтверждения и правдивость исходных данных,
не составляет расписание и не измеряет производительность команды. Компетенции
называются согласованными строковыми обозначениями; сложную работу следует
разбивать. Условная оценка не является разрешением действовать. Выбор владельца,
его сроки и обязательства инструмент не меняет. Новых зависимостей и сервисов нет.

Демонстрация: `python scripts/verify_feasibility_demo.py` — три исхода и доступная
бумажная альтернатива в авторском вымышленном примере. Это тест контракта
инструментов, не LLM benchmark и не доказательство рыночной эффективности.
